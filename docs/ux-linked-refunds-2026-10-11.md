# UX 第九批：从原消费记录退款 · 2026-10-11

基于已验证主线 `ca319fd`，处理产品评估 O14：从消费详情直接记录退款，并能沿关联关系查看原消费与退款。

## 行为

- 消费详情的关联退款区提供“记录退款”。新表单预填原消费的卡片、交易币种及关联关系，金额留空；沿用已有退款金额、促销分配与超额确认流程。账户额度币种不同也不会覆盖原消费的交易币种。
- 所有新增交易入口继续共用草稿恢复。存在未完成草稿时，先选择继续原草稿或丢弃后新建退款；继续的草稿保留自己的类型、卡片、金额、币种及关联事实。未修改的预填表单可直接关闭，不留下空草稿。
- 原消费和退款行成为原生详情导航入口；共享同一个 NavigationStack，原生返回保留上下文。详情内容与呈现根分开，保存反馈仍只在现有详情根显示，编辑弹层继续登记到原有呈现追踪。
- 已冲正的消费仍可关联退款，录入处显示说明；退款作为独立事实保存，不自动冲正、不修改原消费金额。未关联退款沿用原有显示和编辑能力。
- 关联退款按交易日期由近到远排列，同日按稳定 UUID 排序。入口至少 44 点；辅助字号下关联行纵向排列金额与摘要。

本批不改变持久化 Schema、备份格式、退款／促销计算、草稿格式或通知规则，不增加第三方依赖。

## 验证

- 独立 Debug 模拟器场景包含账户额度 HKD、原消费 CNY、已关联部分退款、已冲正原消费和未关联退款。完整备份往返检查交易关系、币种、分配及净进度。
- UI 回归覆盖原消费预填、第二次部分退款、累计超额取消／确认、促销可退余额、保存后重启读回及关联详情往返；另检查已有无关草稿的继续／丢弃、空表单关闭与空金额换卡时币种保护。
- 最大辅助字号回归覆盖已冲正原消费的新退款、独立有效状态、关联导航、44 点入口及点击区域审计，并保留原生截图。

本地 Swift 6 语法解析及 diff 检查为补充；Linux 没有 iOS SDK。交付通过完整 GitHub iOS workflow，预计 203 项单元／集成测试和 28 项 UI 测试；最终 HEAD 全部通过、原生截图确认后合并，并再次验证 main。

初次 [PR 原生运行](https://github.com/maxduke/card-pilot/actions/runs/38127432095) 通过全部 203 项单元／集成测试，但四项新增退款 UI 回归未能正确进入表单，运行在 35 分钟作业上限被取消，未完成完整 UI 套件。已完成的 22 项 UI 测试合计约 24 分钟，构建与其余测试需要额外时间，因此作业预算调整为 50 分钟；每项测试的 180／240 秒限制、完整测试范围和原生产物保留规则不变。退款入口问题修复后需重新通过完整 workflow，不以单元测试通过代替 UI 验收。

失败产物显示：普通字号下入口尚在底部可视范围外，测试却按“可点击”判定直接点击；最大字号下两项独立弹层状态先构造了编辑表单，再切换到新增退款，已有 SwiftUI 表单状态没有重新初始化。修复为单一可识别的编辑／退款弹层目标，内容直接使用目标参数，避免先创建错误表单；测试在点击前检查入口完整可见，并增加已冲正原消费的退款类型与预选关系检查。

第二次 [PR 原生运行](https://github.com/maxduke/card-pilot/actions/runs/38130310567) 完成完整 workflow，203 项单元／集成测试通过，前三项新增退款 UI 回归通过；最大字号保存后的关联导航仍失败。原生层级显示保存提示占用约 233 点高度，详情导航随之下移，而测试对所有页面固定扣除 90 点底栏空间。修复回归为先核对并手动关闭真实保存提示，再查找关联退款；可视区域计算改为只扣除实际可点击的底栏，弹层保留底部安全余量。关联按钮的完整可见、最小点击区域及导航读回检查继续保留，需再次通过完整原生 workflow。

第三次 [PR 原生运行](https://github.com/maxduke/card-pilot/actions/runs/38133400909) 通过 203 项单元／集成测试和 27 项 UI 测试；最大字号回归在保存前的冲正说明检查失败，后续关联导航尚未执行。失败时原生层级显示说明高约 283 点，金额键盘仍保持焦点，说明末尾被固定保存栏遮住；滚动中反复越过可完整阅读的位置。交易表单改为开始滚动时收起键盘，给说明和后续字段留出阅读空间；再次点击输入框仍可继续输入。回归增加滚动后键盘已收起的检查，继续要求完整说明可见以及保存后关联导航通过。测试范围、逐项时限和点击区域检查均不变。

第四次 [PR 原生运行](https://github.com/maxduke/card-pilot/actions/runs/38136270775) 通过全部 203 项单元／集成测试，但完整 UI 验证未通过。逐项日志记录三项失败：最大字号关联导航返回后的断言、保存提示回归中的金额框可点击性查询，以及套件首次启动时的系统后台断言获取超时。测试进程重启后的聚合失败数与逐项记录不一致，因此不据此宣称 UI 通过数量。

原生时间线确认最大字号回归实际点击了“交易详情”返回按钮；12:11:00.143 的失败采集层级与最终截图都显示已经回到原消费，保留了底部关联退款的位置。测试却等待已离开可视区、被懒加载移除的商户标题，随后在失败收尾时触及原有时限。回归改为在原消费标题可见时核对商户和冲正状态，返回时核对根详情“完成”按钮、退款入口，以及同一 UUID 关联行的完整可见和原滚动位置；明确按标签选择原生返回按钮。44 点、完整说明／关联行和点击区域审计继续保留。

保存提示回归的失败层级显示金额框位于 y=396～469.3，保存按钮从 y=479.7 开始，但按钮外侧 10 点留白及分隔线使表单实际只到约 y=468.7。原助手先查询 `isHittable`，对这项被页脚轻微遮挡的输入框触发了 XCTest 的 activation-point 错误。助手现先检查几何边界，扣除整个保存栏，再滚动并查询可点击性；同一次滚动判断复用边界结果。此次修复仅调整 UI 回归与其助手，没有进一步修改生产界面。

首次启动失败发生在建立自动化会话前；最终截图显示应用已进入首页，现有证据指向模拟器／XCTest 启动交接超时，尚不能证明其底层系统原因。保留该失败，不添加重试或跳过。上述修复仍需在最终 HEAD 重新完成全部 203 项单元／集成、28 项 UI（零失败、零跳过）及六张退款验收截图，再通过合并与主线验证。
