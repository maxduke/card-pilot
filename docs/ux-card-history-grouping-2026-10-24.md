# 第二十七批：单卡交易历史复用分组

基于第二十六批已验证主线 `4de8323`。其原生采样证实，全量交易页在每个 Section 读取计算属性会重复筛选、分组和排序整个结果集。单卡入口 `CardTransactionHistoryView` 仍使用同样的写法：`transactionSections[index]` 再次筛选全部交易，再对该卡全部记录分组。

本批在 `body` 中读取该卡已有的 `card.transactions` 逆向关系，在非空分支计算一次分组，所有 Section 读取同一份结果。列表沿用该关系定义的卡片范围，分组函数继续确定日期／UUID 顺序，Section 索引及各行身份保持原样；空状态、详情、使用当前卡添加交易和编辑器的全量上下文保持原样。没有跨更新缓存、额外状态、后台模型访问或 Schema 变化。

新增一项真实 UI 回归，复用已有两万笔隔离夹具：20 张卡、每卡一千笔、五年日期范围。通过卡片搜索进入末张卡，核对一千笔统计、最新行及另一行的卡片身份；从单卡历史添加新交易，检查列表立即出现一次、卡片和金额正确，并返回卡片核对统计变为一千零一笔。三个界面检查点保留原图，复用现有输入、滚动、保存与等待能力。

原有 85 项 UI 用例保持原样，常规原生回归成为 223 项单元／集成加 86 项 UI，共 309 项。先执行新增用例的原生预检，再走正式 PR、完整 CI、适用审查与原图检查、合并主线验证。工作流与原有预算不变。

首次[原生预检 40087999091](https://github.com/maxduke/card-pilot/actions/runs/40087999091) 在默认 180 秒后被终止并触发测试进程自动重启，整体不算通过。实际日志中，首次造数／启动至约 99 秒；单卡页面从点击入口到就绪约 4 秒，一千笔统计、两行的卡片范围及原图均已取得。完整添加流程在第 176.52 秒首次点击保存，尚未完成最终列表与统计断言。现仅为这条完整流程设置仓库已有的 240 秒单项上限，保留全部数据、原断言和工作流的 180／240 秒配置；不把超时后的继续执行或第二次点击计作成功。

[第二次预检 40089041534](https://github.com/maxduke/card-pilot/actions/runs/40089041534) 仍因 240 秒总时限失败，单卡历史检查通过，但确认保存后未完成最终断言。原 App 控制台记录确认保存后的主循环就绪回复延迟至测试连接失效附近；原始结果没有调用栈采样，尚不能归因于某段计算。保留该次失败与自动测试进程重启记录，下一次仅增加确认保存时的原生 App／UI 测试进程调用栈采样，不继续提高时限或修改业务断言。

[采样运行 40105655518](https://github.com/maxduke/card-pilot/actions/runs/40105655518) 在诊断源码 `cadf807` 上以 162.541 秒通过原断言，零失败、跳过、重跑或测试进程重启；这不改变前两次失败的结果。确认保存后取得的五秒原生 App／UI 测试进程采样显示，App 主线程 365 个样本中有 169 个经过 `CardTransactionHistoryView.body` 第 405 行的 `allTransactions` 查询 getter，再进入 SwiftData／CoreData 的关系读取与解码。它支持列表仍读取整个账本这一具体成本，不能证明全部超时原因。

因此在复用分组之外，让列表直接读取本就供卡片统计使用的 `card.transactions`，避免在列表中读出全量查询后按卡片再次筛选。完整查询继续供交易详情和编辑器使用，保留退款及切换卡片的上下文。接下来用同一规模、原断言和 240 秒上限验证该改动；采样结果不冒记为新源码的测量或提升比例。

该 Debug 流程验证大数据下页面可完成操作及数据更新，不替代 Release 耗时、峰值内存或真机流畅度测量，也不产生新的性能提升百分比。第二十六批 21 项实际基线仍属于记录中的诊断源码，不能冒记为本批二进制的测量。现阶段已完成源码修改，原生预检与正式交付仍待执行。
