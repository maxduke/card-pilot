# 可叠加活动的自动预选

## 问题与修复

用户反馈：任意金额活动与单笔满 20 活动都允许叠加，消费 24 时只有前者默认勾选。

确认页会收集全部自动候选，并没有只取第一个。可复现的限制在 `PromotionCalculator.shouldAutomaticallySelect`：配置了优惠笔数上限的逐笔活动一律返回不预选，金额达到单笔门槛也不例外。仅设置单笔门槛的普通累计活动原本就能参与预选；用户真机上第二个活动的具体进度配置仍待确认。

现在逐笔活动同样根据报名状态、币种、单笔金额和可用笔数给出预选。最后一个可用优惠仍参与预选；笔数已用完则保持未勾选。退款不释放优惠笔数，冲正原消费才释放。累计活动的金额上限、多个候选不可叠加时的手动选择、用户手动取消后的选择均沿用原逻辑。确认页说明同步更新，商户、渠道等文字条款仍需用户核对。

不改动模型、备份格式、已保存交易或已有草稿中的手动选择。

## 验证

- 计算器回归：累计和逐笔两种模式下，20／24 达标、19.99 未达标、零金额、跨币种与未报名；逐笔最后一笔、用完、退款不释放、冲正释放。
- 原生 UI 回归：消费 24 同时预选两个可叠加活动，各计入 24，保存后重启读回两条分配。
- 原生 UI 回归：从 19 改为 24 后逐笔活动加入预选；手动取消后改为 25，保留取消状态，累计活动金额更新。
- Linux 本地 Swift 6.0.3：五个变更的 Swift 文件语法检查通过。使用未改写的生产计算器源码、普通模型替身和三个真实 XCTest 方法验证规则：基线代码出现六处预期失败，修复后三个方法均通过。该结果仅覆盖计算规则，不替代 SwiftData 或原生 UI 验证；证据保存在 `/tmp/cardpilot-stackable-preselection-validation`。
- CI 分区选择检查：246 项单元／集成与 104 项 UI，共 350 项；两分区为 298 和 52，完整且无重叠。小屏五项保留。
- 当前宿主为 Linux，原生 SwiftData／SwiftUI 验证需由 iOS CI 执行；此处不预先记录为通过。
