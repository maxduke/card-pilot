# 早期 V3 零金额计入的备份兼容

v0.1.2／v0.1.3 的交易编辑器和活动计入编辑器允许保存零金额，模型校验也接受 `>= 0`。
v0.1.4 开始要求正金额。旧事实仍可能存在于原账本中；当前备份重建复用新录入的严格校验，
会拒绝整个账本的导出和恢复。直接删除这些记录会丢失原有计入关系。

## 直接来源

已核对 GitHub 发布记录：v0.1.0–v0.1.7 均有非草稿、非预发布的 IPA。下载数量不能证明实际账本使用。
v0.1.2 与 v0.1.3 模型源码相同；本批原生样本固定使用
[`3553b38`](https://github.com/maxduke/card-pilot/tree/3553b38c19dbb38004d201bdfa7600648b35e6ee)，
其 `TransactionsView.save`、活动计入编辑器及 `PromotionAllocation.validate` 均明确允许零金额。

v0.1.4 只在这一 V3 家族新增可选优惠笔数上限并收紧计入校验。v0.1.5–v0.1.7 的已有原生样本
覆盖后来定义；它不能代替早期字段集合或零金额事实的验证。

## 最小修正

`PromotionAllocation.validate` 默认仍要求正金额，仅增加显式的历史备份读取选项。
只有 `BackupRecords.insertIntoEmptyStore` 使用该选项，允许精确的零，负数仍然拒绝。
交易与活动计入的新建／编辑沿用原有调用与错误反馈，不自动修正、删除或重新分配历史记录。

没有增加持久化标记、Schema 字段、备份版本、迁移框架或历史模型副本。UUID、金额、币种、
原消费／退款关系及手动计入事实保持原值。

## 原生输入和门禁

临时诊断文件在实际旧源码上构造并保存九类模型的 27 条合成记录，其中包含一条有效消费的零金额计入，
以及正计入、部分退款、共享／关闭账户、历史账期和系列。SQLite backup API 包含已提交 WAL；
另开副本读回并比较所有已保存字段。生产模型和工程不改动。

旧版本没有完整备份功能，因此旁边的 expected-records JSON 是诊断增加的原生字段快照，
不是旧版导出。模型定义来自旧源码，不能用当前模型生成文件后冒充历史数据库。

三项当前原生测试分别验证所有字段升级保存后重开、零计入导出恢复并重启，以及保存失败时保留原账本。
同时保留默认正金额校验和负数拒绝的断言。正式交付要求当前 HEAD 与合并主线均通过 330 项；
专项通过不能代替完整门禁，Linux 语法解析也不能代替 Apple SDK 和 SwiftData 实际运行。

最初的诊断运行 `41026650412` 在辅助枚举缺项处编译失败，执行零条测试；修正只补齐诊断枚举成员，
旧生产代码保持原样。[修正后的生成运行](https://github.com/maxduke/card-pilot/actions/runs/41027239031)
使用诊断源码 `787154b`，一次通过一项，零失败、零跳过；原生 27 条数据、原模型与工程来源、文件
字节和校验值已核对。当前版本的升级、备份与恢复须使用独立运行验证，不能用样本生成成功代替。

## 支持范围

V1／V2 使用不同存储身份，且 V1 含单卡组织关系与旧促销目标定义。它们是否存在需要保留的实际账本
仍需核对；本批保留原文件，不把早期 V3 样本当作 V1／V2 迁移证明。
原生样本也不能代替真实旧设备、iOS 17 或 VoiceOver 验收。
