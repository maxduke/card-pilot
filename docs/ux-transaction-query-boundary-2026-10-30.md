# 交易查询与输入状态边界

交易页面在同一视图中拥有三个 SwiftData 查询以及搜索、筛选和编辑状态。两万笔账本的真实搜索取证
显示，搜索期间的界面更新会进入交易查询的读取路径。本批将查询与这些输入状态分开，
保留同一套筛选、列表、编辑和保存实现。

## 直接证据

[原生运行 40988141223](https://github.com/maxduke/card-pilot/actions/runs/40988141223) 使用诊断源码
`7e0fef8`，对应已验证主线 `40428a5`，只增加临时取证 workflow、一个诊断方法和采集脚本。
Release、Xcode 16.4、macOS 15.8.2、iPhone 16 Pro／iOS 18.5 模拟器下，一条完整诊断流程通过：
五次输入 `73519`，每次精确得到 200 条结果，清空后恢复 20,000 条。最终该次原图已实际验收。

数据准备、重启、列表就绪及搜索框聚焦后发出 UTC 标记；02:01:02.947–02:01:05.170 的目标进程
spindump 位于第一次查询期间，记录实际采样 2.15 秒、188 步、10 毫秒间隔。主线程的 188 个样本均经
`TransactionsView.body` → `filteredTransactions` → `transactions` 的 `@Query` 访问器，继续进入
SwiftData 的编码／解码及 Core Data 关系读取；该线程记录 2.118 秒 CPU 时间。它支持本次窗口内的
具体取数路径，不能推定整个搜索过程的占比、全部瓶颈或真机表现。先前普通 `sample` 超时仍保留，
未把进程号或 CPU 百分比当作调用栈。

## 实现

`TransactionsView` 保留原有三个 `@Query`、排序及 `onAddCard` 入口，将其模型数组传给同位置、
身份稳定的私有 `TransactionListContent`。原搜索／筛选／编辑状态、环境、导航、列表与全部业务助手
一起保留在内容视图中；内容视图的输入更新读取收到的数组，数据变化仍由父视图的原查询驱动。

界面声明、筛选函数、日期和 UUID 顺序、交易动作及保存回滚不变。没有引入跨更新缓存、查询索引、
防抖、后台 SwiftData 传递或额外状态管理，也不改变 Schema、备份、草稿、通知或测量基线。

新增一条真实 UI 回归：八笔夹具中选择消费后显示六笔，保存一笔匹配消费后立即显示七笔并保留筛选；
清除后显示九笔，重启后仍是九笔且新商户唯一。该流程专门保护查询更新传入内容视图时的状态与刷新。
原有 95 项 UI 方法及业务断言保留，必跑门禁变为 231 项单元／集成加 96 项 UI。

## 原生预检中的定位修正

[首次预检 40994014079](https://github.com/maxduke/card-pilot/actions/runs/40994014079) 的新增 UI 流程
在卡片选择阶段失败。当前原图、层级和执行日志确认选择页已打开，宽泛的卡片名称匹配却解析为
底层表单的卡片入口。新用例改为匹配目标卡片身份前缀，检查唯一性、选择页关闭及当前卡片；
