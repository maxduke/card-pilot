# 综合检查后的正确性修复 · 2026-09-29

## 已确认的产品决定

- 新账户录入时，不能漏掉名义账单月在上个月、但还款日仍未过去的账期。按账务规则和常用时区推算初始追踪账期，预览明确显示账期月份、账单日和还款日；是否已经还款仍由用户确认。应用无法自动知道银行余额，不倒推任意逾期历史，也不修改已有账户的追踪起点。
- 新建按月系列时，仅首期保留本次录入的报名事实；后续各期需要报名时从“尚未报名”开始，报名日期为空。“不需要报名”保持不变。复制到下个月同样不复制已报名事实。
- 已有各期的报名状态、报名日期和归档状态属于各期事实；修改系列的共同条款不应覆盖这些事实。

## 正确性边界

审查发现必须与领域规则分开：促销分配是用户确认的事实，修改交易金额不能擅自覆盖分配金额。超过同币种交易金额时应给出清楚警告，并保留用户确认的处理方式。原消费和退款分别拥有冲正状态；冲正原消费不会自动冲正退款，也不改变已定义的进度公式。

先前审查中的 SwiftData 模板自动插入与回滚关系残留属于运行时风险，不是已经在本机复现的事实。本批使用不产生额外模板对象的生成方式、保存前校验及持久化回归测试验证这些路径；原生测试通过之前不宣称完成 SwiftData 验收。

## 金额与草稿兼容

金额输入、编辑值和显示格式采用对应地区的小数及分组符号；输入框金额仍按 `Decimal` 计算，不通过 `Double` 转换，也不把已有高精度金额截为两位。

新交易草稿升级为独立格式 **v2**，记录输入地区以及实际小数／分组符号和分组大小（包括用户的数字格式覆盖）。恢复时保持原金额字符串及完整解析配置，不能仅用地区标识重新创建 `Locale`，否则相同地区下的自定义分隔符可能改变金额。继续兼容 v1 草稿：按旧版固定点号、逗号三位分组规则解释，不依赖平台 POSIX 格式化器的分组默认值。旧应用会拒绝未知 v2 草稿，而不是把新的逗号小数当作千位分隔。SwiftData Schema 与完整 JSON 备份格式不变。

## 已实现范围

- **账期**：新账户与建卡引导共用初始账期计算；预览、确认已还款记录使用同一期，预览变化会清除旧确认。卡片详情不再漏掉上月待还账期，紧凑日程按实际还款日排序，继续保留关闭账户未处理事项。
- **未来规则**：只修改生效月份也会比较该月适用的规则；尚未生效版本可在原月份纠正，不改写已生效历史，也不因修改备注而新增版本。单独删除未来版本的入口仍留待后续。
- **促销系列**：创建复用首期对象，不再保留额外模板；后续期与下月副本不继承报名事实；批量修改保留其他期的报名及归档事实。
- **交易与退款**：同币种超额分配给出明确警告而不擅自覆盖手动金额；退款建议按原分配余额计算，排除已冲正和当前编辑退款；更换卡片会清除无效原消费关联；冲正有关联退款的消费需要确认，不级联冲正。
- **分配选择**：新分配排除已计入该活动的交易，候选优先，无候选时要求手动选择；冲正记录在活动详情显示“不计入”。复制活动增加具体日期确认和完成反馈。
- **恢复与失败处理**：失效草稿活动可移除而保留其余输入；部分保存路径在修改模型前校验，并在失败时恢复涉及的字段和双向关系。过期的入账日期活动不再作为待补日期推荐，仍可手动搜索。
- **金额地区格式**：支持当地小数及合法分组符号、非 ASCII 十进制数字和精确编辑往返；草稿地区固定，设备地区变化时显示说明并提供可输入原分隔符的键盘。

未包含通知权限、应用锁、整体配色／对比度、首页撤销提示及长期数据性能优化。这些仍是后续批次，不应把本批理解为修复了全部审查建议。
