# Released data fixture

`CardPilot-v0.1.7.*` was generated by the actual v0.1.7 application source,
commit `437d303261ec40ed5a7fb7313d2d910da351779f`, with Xcode 16.4 on the
iPhone 16 Pro / iOS 18.5 simulator. It contains synthetic data, not a user's
database or an archive captured from an old device.

The immutable [generator commit](https://github.com/maxduke/card-pilot/commit/02ae83086ca77a62859bacdff5d41366f54acac9)
adds only a diagnostic XCTest and workflow to the released source. The
[native generation run](https://github.com/maxduke/card-pilot/actions/runs/40207397025)
passed once, without failures, skips or restarts. Production files and the
Xcode project were checked against the released commit before generation.

The generator saved through SwiftData, exported through the released backup
API, and saved the draft through the released draft store. SQLite's
[backup API](https://www.sqlite.org/backup.html) included committed WAL
contents in a consistent snapshot. Readback used a separate copy.

The 25 records cover all nine models: one bank, six networks, two accounts,
three cards, four billing rules, two saved cycles, two monthly promotion
periods, three transactions and two allocations. They include a shared
account, a closed account, partial refund relationships, reversed history,
archived promotion information and decimal values. The backup records the
values actually saved by v0.1.7; SwiftData can normalize large Decimal
literals before export. The v1 draft retains the unfinished amount `1,234.`
and manual allocation input `50.125`, without a number-format snapshot.

The three data files are byte-for-byte copies of the native output.
`CardPilot-v0.1.7.manifest.json` is the original `manifest.json` under a
unique resource name; `CardPilot-v0.1.7.provenance.json` is the original
workflow source/provenance report. File sizes and SHA-256 hashes remain in
the manifest and are checked before each native compatibility test.

Keep these inputs immutable. Tests open disposable copies at the same
selected URL, compare every backup field and UUID relationship, save and
reopen, restore/relaunch, check draft identity and preserve data after a
failed staged save. A future schema change must run against these released
inputs. The native compatibility tests now exercise the specific V3-to-V4
upgrade on iOS 18.5. This does not prove other historical model families,
iOS 17, physical-device upgrade, notification delivery or future migrations.

## Early V3 input

`CardPilot-v0.1.3.store` and `CardPilot-v0.1.3.expected-records.json` were generated
from immutable v0.1.3 source `3553b38c19dbb38004d201bdfa7600648b35e6ee`; v0.1.2 has
identical model source. The [generator](https://github.com/maxduke/card-pilot/commit/787154b1c3e14738c19517c129035521e54d7811)
adds only a diagnostic test and workflow. Its [native run](https://github.com/maxduke/card-pilot/actions/runs/41027239031)
passed one test with no failures or skips on Xcode 16.4 / iOS 18.5 simulator.

The 27 records cover the same nine model types, including an active purchase
with a zero HKD allocation accepted by the released editor/model. This input
predates the optional promotion benefit count and account name. SQLite backup
includes committed WAL; an independent copy was reopened with the old models
and compared against every captured field and relationship.

The expected JSON is an added diagnostic serialization of saved native fields,
not a historical backup export: v0.1.3 had no full-backup feature. Payload bytes
are unchanged; the original manifest and provenance were only given unique
`CardPilot-v0.1.3.*.json` resource names. Keep all four inputs immutable and open
only disposable store copies. These inputs do not prove V1/V2 or device migration.
